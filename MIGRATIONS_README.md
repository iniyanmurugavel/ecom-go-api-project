# Migrations, Data, and What Happens When You Change Tables

This file is **just for your learning**. It explains how migrations work (with Goose + PostgreSQL), what happens to **data** when you change a table, and how this fits into your project. Nothing here is implemented automatically; it’s to help you reason about changes safely.

---

## 1. What is a migration?

Think of a migration as a **step in the history of your database schema**:

- Migration 1: create `products` table.
- Migration 2: create `orders` and `order_items` tables.
- Migration N: add columns, indexes, new tables, etc.

Each migration file describes:

- **`Up`**: how to move **forward** (apply the change).
- **`Down`**: how to move **backward** (undo the change).

In this project (Goose):

- `internal/adapters/postgresql/migrations/00001_create_products.sql`
- `internal/adapters/postgresql/migrations/00002_create_orders.sql`

Example (simplified):

```sql
-- +goose Up
-- +goose StatementBegin
CREATE TABLE IF NOT EXISTS products (...);
-- +goose StatementEnd

-- +goose Down
-- +goose StatementBegin
DROP TABLE IF EXISTS products;
-- +goose StatementEnd
```

When you run:

```bash
goose up
```

Goose applies each **Up** in order (1, 2, 3, …).  
When you run:

```bash
goose down
```

Goose applies the **Down** of the latest migration (rolls back one step).

> In real projects, you **almost never** run `down` on production because it can drop data. You mostly move **forward** (new migrations).

## 2. How does this affect data?

The impact on data depends on **what SQL you write in the migration**.

### Case A: `ALTER TABLE` to add a column

Example:

```sql
-- +goose Up
ALTER TABLE products ADD COLUMN description TEXT;
```

What happens:

- Existing rows keep all their current values.
- New column `description` is `NULL` (or default) for existing rows.
- No existing data is lost.

If you add a **NOT NULL** column **with a default**:

```sql
ALTER TABLE products
ADD COLUMN is_active BOOLEAN NOT NULL DEFAULT true;
```

- PostgreSQL sets `is_active = true` for **existing** rows.
- Future inserts must set a value or use the default.

### Case B: `ALTER TABLE` to drop a column

```sql
ALTER TABLE products DROP COLUMN price_in_centers;
```

What happens:

- **All data in that column is permanently removed**.
- Your Go structs generated by SQLC will also change (on the next `sqlc generate`).
- Any queries referring to that column will **break** until you update them.

So: dropping columns **deletes data**. Only do this when you are sure you don’t need it, or you have copied it somewhere else.

### Case C: `DROP TABLE`

```sql
DROP TABLE IF EXISTS products;
```

What happens:

- The whole table and **all rows are deleted**.
- This is what your `Down` migrations currently do for `products` and `orders`.

In practice:

- You use `DROP TABLE` in `Down` mainly for local/dev rollback.
- You rarely run `Down` on production because it discards data.

## 3. Changing a table “itself” – examples

### 3.1. Add a new column (safe, very common)

Say you want `products` to have a `sku`:

```sql
-- +goose Up
ALTER TABLE products ADD COLUMN sku TEXT;

-- +goose Down
ALTER TABLE products DROP COLUMN sku;
```

Effect:

- No existing rows are removed.
- `sku` is `NULL` for older rows until you update them or enforce constraints.

### 3.2. Rename a column

PostgreSQL supports rename:

```sql
ALTER TABLE products RENAME COLUMN price_in_centers TO price_in_cents;
```

Effect:

- Data is kept.
- Your Go code and queries must change to use the **new column name**.
- After changing the migration/schema, you run `sqlc generate` so the generated Go structs and queries match the new column name.

### 3.3. Change column type

Example:

```sql
ALTER TABLE products
ALTER COLUMN price_in_centers TYPE BIGINT;
```

Effect:

- PostgreSQL tries to **convert existing values** to the new type.
- If conversion fails for some row, the migration fails.

Typical pattern:

- Sometimes you add a new column, copy data over, then drop the old one if you need a more complex change:
  - `new_price BIGINT`
  - `UPDATE products SET new_price = price_in_centers;`
  - Remove old column later.

### 3.4. Add NOT NULL to an existing column

```sql
ALTER TABLE products
ALTER COLUMN name SET NOT NULL;
```

Effect:

- If **any existing row** has `name IS NULL`, the migration fails.
- Before adding NOT NULL, you usually clean up the data:
  - `UPDATE products SET name = 'unknown' WHERE name IS NULL;`

## 4. How migrations fit into your project

### Files

- `internal/adapters/postgresql/migrations/*.sql`  
  - History of how to build/change the schema.
  - Goose uses these to update your real PostgreSQL in Docker.
- `internal/adapters/postgresql/sqlc/queries.sql`  
  - The exact SQL your app runs (SELECT/INSERT/UPDATE).
- `sqlc.yaml`  
  - Tells SQLC where the schema (migrations) and queries are.\n

### Workflow for schema changes

When you **change a table** or add a new one:

1. **Write a new migration file** (e.g. `00003_add_sku_to_products.sql`) with `Up` / `Down`.
2. **Run migrations** so the **real DB** changes:
   ```bash
   source .env   # or export GOOSE_* from .env
   goose up      # applies new migration(s)
   ```
3. **Regenerate SQLC code**:
   ```bash
   sqlc generate
   ```
   - SQLC reads the updated schema + queries and updates Go structs/methods.
4. **Update services/handlers** to use any new fields or queries.
5. **Restart the API** (`go run cmd/*.go` or `air`).

> Important: the **data currently in the DB** is affected only by what your migration SQL does (ALTER TABLE, DROP COLUMN, etc.). SQLC just regenerates Go code to match the new schema; it does not move or delete data by itself.

## 5. What happens to my data if I…?

Short answers:

- **Add a column**: Existing rows keep their data; new column is NULL or default for old rows.\n
- **Drop a column**: Data in that column is **lost** (for all rows).\n
- **Add a table**: No impact on existing tables’ data.\n
- **Drop a table**: All rows in that table are **deleted**.\n
- **Rename a column**: Data stays; name changes; code + queries must update.\n
- **Change column type**: PostgreSQL tries to convert; if conversion fails, migration fails.\n
- **Add NOT NULL**: Fails if some rows have NULL there; usually you clean the data first.\n

For local/dev you can afford to drop and recreate tables. For production you usually:\n
- Only move **forwards** (new migrations).\n
- Avoid dropping tables/columns until you are sure you no longer need that data.\n

## 6. Migrations + Docker + Hot Reload (summary)

This is how everything works together in your project:

- **Docker**: Runs Postgres (real data lives here).
- **Goose**: Applies migrations to that Postgres (schema changes, not code).
- **SQLC**: Reads migrations + queries, generates Go repo code that knows about tables/columns.\n
- **Your Go API**: Uses that repo code; when you change schema/queries, you regenerate and restart.\n
- **Hot reload tools (like air)**: Restart your Go app when code changes, but they **do not** run migrations or SQLC for you. You still run `goose up` and `sqlc generate` manually when you change schema or queries.\n

Use this file as your personal reference when you ask: “If I change this table, what happens to my data?” or “What commands do I run after I change schema or queries?”.\n

## 7. Why don't I see my data when I open the database? (API returns data but DB client shows empty)

**What you see:** The API returns products and orders (e.g. GET /products shows 3 products, POST /orders returns order id 10). But when you open "the database" in a GUI (pgAdmin, DBeaver, TablePlus, etc.) or run a query somewhere, the tables look empty or you don't see those rows.

**Why:** Your app and your DB client are talking to **different PostgreSQL instances**.

- The **API** uses the connection from `.env`: **port 15432**, database **ecom**, user **postgres** (this is the **Docker** Postgres).
- Many DB clients default to **port 5432**. On your Mac, something else (e.g. Postgres.app, Homebrew Postgres) often runs on 5432. That is a **different** server and a **different** database. It has no `ecom` database or no data in it.

So the data **is** in the database – but in the one listening on **15432** (Docker), not 5432.

**What to do:**

1. **Connect your DB client to the same database the API uses:**
   - **Host:** localhost
   - **Port:** 15432 (not 5432)
   - **Database:** ecom
   - **User:** postgres
   - **Password:** postgres

   After that, you should see the same products and orders (and order_items) that the API reads and writes.

2. **Or view data from the terminal (no GUI):**
   ```bash
   docker exec ecom-postgres psql -U postgres -d ecom -c "SELECT * FROM products;"
   docker exec ecom-postgres psql -U postgres -d ecom -c "SELECT * FROM orders ORDER BY id DESC LIMIT 10;"
   docker exec ecom-postgres psql -U postgres -d ecom -c "SELECT * FROM order_items;"
   ```
   This runs SQL inside the Docker Postgres container, so you always see the same data as the API.

**Summary:** The API works because it connects to Postgres on **port 15432** (Docker). To see that same data, your DB client must also use **port 15432** and database **ecom**. If you use port 5432, you're looking at a different server where the ecom data does not exist.
