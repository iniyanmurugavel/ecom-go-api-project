# High-Level Design: How This API Works

This document explains how a request flows from the client to the database, how SQLC and Docker fit in, and what you need to do when you make changes (including hot reload).

---

## 1. Big Picture: Request Flow

```
  Postman/curl                    Your Go app (runs on host)              Docker
  ────────────                   ──────────────────────────              ─────
       │                                    │                                  │
       │  GET /products                     │                                  │
       │  POST /orders                      │                                  │
       ▼                                    │                                  │
  ┌─────────┐    ┌─────────┐    ┌─────────┐│   ┌─────────┐    ┌──────────────┐
  │  Chi    │───▶│ Handler │───▶│ Service ││──▶│  Repo   │───▶│  PostgreSQL  │
  │ Router  │    │ (HTTP)  │    │ (logic)  ││   │ (sqlc)  │    │  (container) │
  └─────────┘    └─────────┘    └─────────┘│   └─────────┘    └──────────────┘
       │                │             │    │         │                │
       │                │             │    │         │                │
  • Route matching  • Parse JSON   • Validate   • Generated   • Real DB
  • Middleware      • Status codes • Transaction  Go code      • port 15432
  • Timeout         • Call service • Call repo    runs SQL      on host
```

- **Chi**: HTTP router. Matches URL + method to a handler, runs middleware (log, recover, timeout).
- **Handler**: HTTP layer. Reads body, calls service, maps errors to status codes (400, 404, 500), writes JSON.
- **Service**: Business logic. Validates input, runs in a transaction for orders, calls repo to read/write DB.
- **Repo**: Data access. **Generated by SQLC** from your SQL; talks to PostgreSQL.
- **PostgreSQL**: Runs **inside Docker**. Your app connects to it at `localhost:15432`.

The Go binary runs on your machine; only the database runs in Docker. No need to put the API in Docker for local dev.

## 2. Flow for Two Example Requests

### GET /products

1. **Chi** matches `GET /products` → `products.ListProducts` handler.
2. **Handler** calls `service.ListProducts(ctx)`.
3. **Service** calls `repo.ListProducts(ctx)` (repo = sqlc-generated `Queries`).
4. **Repo** runs `SELECT * FROM products` (from `queries.sql`), returns `[]Product`.
5. **Handler** writes JSON with `json.Write(w, 200, products)`.
6. Client gets the JSON response.

No transaction needed; one read-only query.

### POST /orders

1. **Chi** matches `POST /orders` → `orders.PlaceOrder` handler.
2. **Handler** reads body with `json.Read(r, &tempOrder)` (customerId, items[]).
3. **Handler** calls `service.PlaceOrder(ctx, tempOrder)`.
4. **Service**:
   - Validates (customerId, at least one item).
   - Starts a **transaction**: `tx := db.Begin(ctx)`.
   - Uses **repo with that transaction**: `qtx := repo.WithTx(tx)` so all queries run in the same tx.
   - Creates order: `qtx.CreateOrder(ctx, customerId)`.
   - For each item: finds product, checks stock, `qtx.CreateOrderItem(...)`.
   - On success: `tx.Commit(ctx)`; on error: `defer tx.Rollback(ctx)`.
5. **Repo** runs the SQL from `queries.sql` (CreateOrder, FindProductByID, CreateOrderItem).
6. **Handler** returns 201 + order JSON (or 400/404/500 on error).

Critical point: the **service** owns the transaction; the **repo** just runs the SQL you defined in `queries.sql`.

## 3. Where SQLC and Code Generation Fit

SQLC **generates** Go code from:
- **Schema**: tables and columns. It reads your **migration files** in `internal/adapters/postgresql/migrations/` (e.g. `00001_create_products.sql`, `00002_create_orders.sql`).
- **Queries**: the SQL you write in `internal/adapters/postgresql/sqlc/queries.sql` (e.g. `ListProducts`, `CreateOrder`).

When you run `sqlc generate`:

- It reads `sqlc.yaml` (which points to the migrations folder and `queries.sql`).
- It generates:
  - **Models**: Go structs like `Product`, `Order`, `OrderItem` (from the schema).
  - **Queries**: Go methods like `ListProducts(ctx)`, `CreateOrder(ctx, customerID)` (from the SQL in `queries.sql`).
  - **Querier interface**: so your service depends on an interface, not the concrete type.

So the chain is:

```
  You write                    SQLC generates                 Your code uses
  ─────────                    ─────────────                 ───────────────
  migrations/*.sql      →      models (Product, Order…)       repo.Product, repo.Order
  sqlc/queries.sql      →      Queries methods                repo.ListProducts(), repo.CreateOrder()
  sqlc.yaml             →      package repo in sqlc/           import repo "…/sqlc"
```

The **repo** package is the only place that talks to PostgreSQL in this project; handlers and services never write raw SQL.

## 4. Where Docker Fits

- **Docker** runs **only PostgreSQL** for this project (see `docker-compose.yaml`).
- The **API** runs on your host: `go run cmd/*.go` (or a built binary). It is **not** in Docker by default.
- The app connects to the DB at `localhost:15432` (host port 15432 → container port 5432).

So:

- **Docker up** = database is available.
- **Docker down** = database is gone; the app will fail to connect.
- You do **not** need to rebuild or restart Docker when you change **Go code** or **queries.sql**. You only need Docker running so the app can connect.

When you change the **schema** (new table/column), you run **migrations** so the real DB in Docker matches the new schema; that is the next section.

## 5. When You Make a Change: What to Update

Use this as a checklist so changes reflect correctly.

### A) You change **Go code** (handlers, services, main, etc.)

- **Reflect how?** Rebuild and run the app.
- **Steps:**
  1. Stop the running API (Ctrl+C).
  2. `go run cmd/*.go` (or `go build` then run the binary).
- **Docker:** No change. Keep `docker compose up -d` so Postgres is running.
- **Hot reload (optional):** Use a tool like [air](https://github.com/air-verse/air) so the server restarts when you save a `.go` file. Example:
  ```bash
  go install github.com/air-verse/air@latest
  air
  ```
  Then edit a handler or service and save; the API restarts and your change is live.

### B) You add or change a **SQL query** (in `queries.sql`)

- **Reflect how?** Regenerate repo code, then rebuild/run the app.
- **Steps:**
  1. Edit `internal/adapters/postgresql/sqlc/queries.sql` (add a new `-- name: QueryName :one|:many` block).
  2. Run **`sqlc generate`**. This regenerates the Go code in `internal/adapters/postgresql/sqlc/` (e.g. a new method on `Queries`).
  3. Use the new method in your service (e.g. `repo.FindProductByID`).
  4. Restart the API: `go run cmd/*.go` (or use air).
- **Docker:** No change. Migrations only if the query uses new tables/columns (see C).
- **No hot reload for SQL:** Changing only `queries.sql` does not restart the app; you must run `sqlc generate` and restart.

### C) You change the **database schema** (new table, new column)

- **Reflect how?** Migration to update the real DB + SQLC regenerate so Go types match.
- **Steps:**
  1. Add a **migration** in `internal/adapters/postgresql/migrations/` (e.g. `00003_add_foo.sql`). Use goose format (`-- +goose Up` / `-- +goose Down`).
  2. Run **migrations** against the DB in Docker:
     ```bash
     source .env   # or export GOOSE_* from .env
     goose up
     ```
     Now the **PostgreSQL in Docker** has the new table/column.
  3. Run **`sqlc generate`**. SQLC reads the migrations (including the new one) and regenerates models and query code. Your `queries.sql` can now reference the new schema.
  4. If you added new queries in `queries.sql`, use them in the service; then restart the API.
- **Docker:** You do **not** rebuild the Docker image. You only run `goose up` so the **existing** Postgres container’s database is updated. Restarting the container (e.g. `docker compose restart`) is only needed if you change something like Postgres config or the image itself.

### D) You change **.env** (DB URL, port, HTTP port)

- **Reflect how?** Restart the API so it reloads `.env` (via `godotenv.Load(".env")`).
- **Docker:** No change unless you change the DB host/port to point elsewhere.

### E) Summary Table

| What changed           | Run migrations? | Run sqlc generate? | Restart API? | Docker?        |
|------------------------|-----------------|--------------------|--------------|----------------|
| Go code only           | No              | No                 | Yes          | No             |
| queries.sql only       | No              | Yes                | Yes          | No             |
| Schema (migrations)    | Yes (`goose up`)| Yes                | Yes          | No (just run)  |
| .env                   | No              | No                 | Yes          | No             |

## 6. Hot Reload (Optional)

By default there is **no** hot reload: you restart the API manually after changes.

To get **automatic restart on Go changes**:

1. Install **air** (or similar):
   ```bash
   go install github.com/air-verse/air@latest
   ```
2. From the project root, run:
   ```bash
   air
   ```
   Air watches `.go` files and runs `go build` + restarts the server when you save.

Note: Air does **not** run `sqlc generate` or `goose up` for you. After schema or query changes, run those yourself, then let air restart the app on the next Go file save (or restart air).

```
When you change:
  • Go code        → restart API (or use air).
  • queries.sql    → sqlc generate, then restart API.
  • migrations     → goose up, then sqlc generate, then restart API.
  • .env           → restart API.
  • Docker image   → docker compose up -d (only if you changed compose or image).
```

This should give you a clear HLD of how the API works and how to make changes (including when to touch Docker, migrations, SQLC, and the running server).
